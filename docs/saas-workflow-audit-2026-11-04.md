# ContentOS workflow audit — 4 November 2026

Audit only. Implementation is awaiting explicit approval. No application, schema, migration, or deployment changes were made by this audit.

## Scope and evidence standard

Reviewed the current, already modified checkout: runtime bootstrap, both authentication guards, OTP/workspace provisioning, subscription schema and entitlement evaluation, billing/admin APIs and React pages, content transitions, direct publishing, YouTube publishing, queue claiming/relay, batch processing, calendar/festival scheduling, knowledge automation, PDF visual concept dispatch, and Instagram creative services. Existing architecture documentation was used as a map and checked against source. This is a source audit with limited automated validation, not a completed live end-to-end or production security certification.

“Verified” below means the defect is visible in the actual source path. It does not mean an exploit was performed against a deployed system. “Needs runtime verification” and “enhancement” are explicitly identified. Line references refer to the current checkout. Existing user changes were not reverted. Generated frontend assets changed during the session without this audit running a build; their producer was not established.

## Architecture and connected workflows

- `app.mjs` imports `dist-api/phase-main.js`. That application registers `PhaseGuard`, `AdminGuard`, and the billing, creative, content, calendar, documents, batch, social, and knowledge controllers (`server/phase-main.ts:171`). The basic `sessions` guard in `server/security.ts` is not the active phase-authentication path.
- Registration and email verification exist in `server/phase-auth.controller.ts:112,151`. Verification/login call `workspaceForUser`; its transaction provisions membership, brand kit, a 120-hour trial, and a TRIALING subscription with a custom limit of 3 (`server/workspace-session.ts:13,56`). Membership-based workspace selection already exists. The separate explicit workspace-creation route has different provisioning, noted below.
- Paid plans, workspace trials/subscriptions, pending payments, subscription events, and administrative audit logs already exist in migration 024. Seed prices and limits are Starter ₹15,000/3, Growth ₹25,000/5, and Scale ₹50,000/10. The highest existing identifier is `SCALE`; preserve it and reconcile its display name with the requested “Business” name through an explicit product decision. No evidence of a different price decision was found in the reviewed configuration.
- `getWorkspaceEntitlement` evaluates expiry dynamically. Standard content creation, review/approval/scheduling, caption generation, and Clipdrop generation call the existing access assertion. Billing/account routes remain accessible through authentication and membership rather than a global subscription lock.
- Purchase submission creates PENDING payment rows without activating access (`server/billing/billing.controller.ts:206`). Admin review uses a separate platform-admin cookie/session and controller guard; workspace Admin/Owner roles do not confer platform administration (`server/admin.controller.ts:59`). Approval and rejection already have endpoints and administrative logs.
- Scheduling uses `validateSchedule`, platform planning, healthy-account selection, and a shared workspace lock in `assertDailySlot`. Queues and publishing claims already have duplicate-delivery, content-version, token-state, and UNCERTAIN protections. These should be extended, not replaced.
- The existing admin UI already provides user search/filtering, profile/security/subscription editing, plan editing, payment review, activity, and audit sections. Its user-detail components are reusable. A duplicate dashboard or billing system is unnecessary.

## Items requiring runtime verification or product decisions

- **Account deactivation and previously queued work:** PhaseGuard blocks inactive accounts immediately (`server/phase-main.ts:73`), but publisher claim evaluates workspace subscription rather than the scheduling user's current account/membership. Clarify whether deactivating one member should cancel their scheduled work or whether workspace-owned schedules should continue. Do not treat continuing shared-workspace jobs as a confirmed security defect without this policy.
- **Cancellation:** cancel-at-period-end is recorded and time-based entitlement eventually locks access. No centralized transition consuming that flag was found in the reviewed expiry paths. Decide whether raw status must become CANCELED, what notifications occur, and how renewals/rejections interact. Loss of access at time expiry already exists; cancellation is not wholly missing.
- **Highest plan label:** SCALE/Scale is consistent across seed, validation, frontend and tests. Required Business pricing/limit already matches that plan. Retain identifier; confirm display naming before changing it.
- **Admin operational visibility (P2 enhancement):** reuse current diagnostics/activity screens to add authoritative daily successful/reserved/remaining quota, jobs blocked by expiry, pending/failed/uncertain publications, and remaining paid days. AI credit accounting was not established as an authoritative existing ledger; do not invent a balance from request counts.
- **Provider integration (needs runtime verification):** account/workspace scoping, token encryption, healthy-account selection and platform capability planning exist. Actual external token refresh, revoked provider access, multi-platform partial failure, YouTube processing and live deletion were not tested against live providers in this audit.
- **Legacy entitlement policy:** migration 024 deliberately backfills existing workspaces with ten-year ADMIN_GRANTED access. This is an explicit compatibility policy, not proof of an unauthorized bypass. Preserve existing grants unless the user approves a migration policy change.
